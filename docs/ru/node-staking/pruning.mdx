# Обрезка клиента исполнения

::: tip ПРИМЕЧАНИЕ
Эта страница описывает путь **офлайн-/онлайн-обрезки** для `geth` и `nethermind` (`rocketpool service prune-eth1`).

Обычный способ держать использование диска под контролем — **Rolling History Expiry** (режим Pruning Mode по умолчанию). Nethermind, Besu, Reth и Erigon удаляют тела блоков и квитанции старше примерно одного года; Geth вместо этого использует удаление истории до Prague. См. [Удаление истории Execution-клиента](./maintenance/history-expiry).

:::

Если вы используете `geth` или `nethermind` в качестве основного клиента исполнения, вы, вероятно, заметите, что свободное место на диске вашего узла медленно уменьшается с течением времени.
Клиент исполнения вносит наибольший вклад в это; в зависимости от того, сколько оперативной памяти вы выделили для его кэша во время `rocketpool service config`, он может расти со скоростью несколько гигабайт в день!

Для решения этой проблемы клиенты исполнения предоставляют специальную функцию, называемую **обрезкой**, которая позволяет им безопасно сканировать и очищать свою базу данных для освобождения свободного места.
Каждому оператору узла, использующему Geth или Nethermind, в конечном итоге придется обрезать его.

Если у вас есть SSD на 2 ТБ, вы обычно можете обходиться месяцами между раундами обрезки.
Для пользователей SSD на 1 ТБ вам придется обрезать чаще.

Если у вас включена [панель Grafana](./grafana), хорошим практическим правилом является начать думать об обрезке вашего клиента исполнения, когда используемое дисковое пространство вашего узла превышает 80%.

Когда вы решите, что пришло время, Smart Node поставляется с возможностью обрезать его для вас по запросу.
Читайте ниже, чтобы узнать, как это работает и чего ожидать.

::: warning ПРИМЕЧАНИЕ
Обрезка вашего клиента исполнения возможна только в режиме Docker.

Если вы используете свой собственный клиент исполнения, такой как внешний клиент в гибридном режиме или Native mode, вы не можете использовать Smart Node для обрезки клиента исполнения.
Вам нужно будет сделать это вручную.
Пожалуйста, обратитесь к документации для вашего клиента исполнения, чтобы узнать, как его обрезать.
:::

## Nethermind 2.0 и FlatDB

Начиная с Smart Node v1.24.3, Smart Node использует **Nethermind 2.0**. Nethermind 2.0 хранит новые базы данных в формате под названием **FlatDB**.
FlatDB не требует ручной обрезки состояния и не поддерживает её. Если ваша база данных Nethermind использует FlatDB, команда `rocketpool service prune-eth1` вам вообще не нужна.

Существующие базы данных Nethermind **не** конвертируются. Если ваш узел был синхронизирован до Nethermind 2.0, он продолжает использовать устаревшую базу данных **Patricia**, и вы можете продолжать обрезать её, как описано на этой странице.
Единственный способ перейти на FlatDB — пересинхронизировать ваш клиент Execution с помощью `rocketpool service resync-eth1`.

::: warning ПРИМЕЧАНИЕ
Перед пересинхронизацией рекомендуем [настроить резервный узел](./fallback) и [проверить, что он работает](./fallback#тестирование-резервных-клиентов).
При настроенном резервном узле Smart Node и ваш клиент Consensus автоматически переключатся на него, пока основной клиент Execution пересинхронизируется, и вернутся обратно после завершения синхронизации.
:::

### Проверьте, какая у вас база данных

Выполните:

```shell
rocketpool service get-db-details
```

| Вывод                                                                           | Что это означает                                                                        |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `Nethermind is using FlatDB. Manual state pruning is not needed or supported.`  | Обрезка не нужна. Остальная часть этой страницы к вам не относится.                     |
| `Nethermind is using the legacy Patricia database. State pruning is supported.` | Выполните описанные ниже шаги обрезки, когда диск начнёт заполняться.                   |
| `Nethermind has no persisted state database yet.`                               | Nethermind ещё не записал никакого состояния (например, сразу после пересинхронизации). |

::: tip ПРИМЕЧАНИЕ
Для работы `get-db-details` контейнер вашего клиента Execution должен быть запущен.
Команда сообщает только формат базы данных. На Archive-узле она может по-прежнему сообщать, что обрезка состояния поддерживается, но Archive-узлы обрезать нельзя.
:::

### FlatInTrie на системах с 16 ГиБ ОЗУ или меньше

Когда Nethermind синхронизирует новую базу данных на машине с **16 ГиБ ОЗУ или меньше**, Smart Node выбирает схему FlatDB **FlatInTrie** от Nethermind, которая лучше подходит для систем с меньшим объёмом памяти.
Этот выбор сохраняется вместе с базой данных, поэтому он не изменится, если вы перезапустите узел или позже добавите ОЗУ.
Он сбрасывается только при пересинхронизации с помощью `rocketpool service resync-eth1`.

### Настройки, применимые только к устаревшей базе данных

Следующие настройки Nethermind в `rocketpool service config` влияют только на устаревшие базы данных Patricia и игнорируются при использовании FlatDB:

- In-Memory Pruning Cache Size
- Full Prune Memory Budget Size
- Prune threshold (MB)
- Full pruning parallelism

::: tip ПРИМЕЧАНИЕ
FlatDB устраняет необходимость обрезать **состояние**. Он не меняет объём **истории** (тела блоков и квитанции), которую хранит ваш узел.
Это по-прежнему определяется настройкой **Pruning Mode**. См. [Истечение истории клиента Execution](./maintenance/history-expiry).
:::

## Миграция Geth на Pebble v2

Если вы используете **Geth** и база данных всё ещё на Pebble v1, выполните миграцию на месте командой:

```shell
rocketpool service migrate-geth
```

Эта команда останавливает Geth, переносит базу данных с Pebble v1 → v2, а затем перезапускает его. Это **не** то же самое, что `prune-eth1`, и команда называется **`migrate-geth`** (а не `migrate-eth1`).

::: warning ПРЕДУПРЕЖДЕНИЕ
На время миграции Geth находится офлайн. Без [резервной ноды](./fallback) вы будете пропускать аттестации и предложения блоков, пока она не завершится.
:::

Подтвердите запрос или передайте `--yes`, чтобы его пропустить. Следите за прогрессом с помощью:

```shell
rocketpool service logs eth1
```

Не прерывайте работу контейнера до завершения миграции.
