# Fazendo Pruning do Cliente Execution

::: tip NOTA
Esta página descreve o caminho de **poda offline / online** para `geth` e `nethermind` (`rocketpool service prune-eth1`).

A forma usual de manter o uso de disco sob controle é o **Rolling History Expiry** (o Pruning Mode padrão). Nethermind, Besu, Reth e Erigon descartam corpos e recibos com mais de aproximadamente um ano; o Geth usa a expiração de histórico anterior ao Prague. Veja [Expiração do Histórico do Cliente de Execução](./maintenance/history-expiry).

:::

Se você usa `geth` ou `nethermind` como seu cliente Execution primário, você provavelmente notará que o espaço livre em disco do seu nó diminui lentamente ao longo do tempo.
O cliente Execution é de longe o maior contribuidor para isso; dependendo de quanta RAM você alocou para seu cache durante `rocketpool service config`, ele pode crescer a uma taxa de vários gigabytes por dia!

Para lidar com isso, os clientes Execution fornecem uma função especial chamada **pruning** que permite que eles escaneiem e limpem seu banco de dados com segurança para recuperar algum espaço livre.
Todo operador de nó usando Geth ou Nethermind terá que fazer pruning eventualmente.

Se você tem um SSD de 2 TB, geralmente pode ir por meses entre rodadas de pruning.
Para usuários de SSD de 1 TB, você terá que fazer pruning com mais frequência.

Se você tem [o painel Grafana](./grafana) habilitado, uma boa regra prática é começar a pensar em fazer pruning do seu cliente Execution quando o espaço em disco usado do seu nó exceder 80%.

Quando decidir que é hora, o Smart Node vem com a capacidade de fazer pruning para você mediante solicitação.
Leia abaixo para aprender como funciona e o que esperar.

::: warning NOTA
Fazer pruning do seu cliente Execution só é possível no Modo Docker.

Se você usa seu próprio cliente Execution, como um cliente externo em modo Híbrido ou modo Nativo, você não pode usar o Smart Node para fazer pruning do cliente Execution.
Você precisará fazer isso manualmente.
Por favor, consulte a documentação do seu cliente Execution para aprender como fazer pruning.
:::

## Nethermind 2.0 e FlatDB

A partir do Smart Node v1.24.3, o Smart Node usa o **Nethermind 2.0**. O Nethermind 2.0 armazena novos bancos de dados em um formato chamado **FlatDB**.
O FlatDB não precisa de pruning manual do estado e não oferece suporte a ele. Se o seu banco de dados do Nethermind usa FlatDB, você não precisa de `rocketpool service prune-eth1` de forma alguma.

Bancos de dados existentes do Nethermind **não** são convertidos. Se o seu node foi sincronizado antes do Nethermind 2.0, ele continua usando o banco de dados **Patricia** legado e você pode continuar fazendo pruning dele conforme descrito nesta página.
A única forma de migrar para o FlatDB é ressincronizar o seu cliente de Execution com `rocketpool service resync-eth1`.

::: warning NOTA
Antes de ressincronizar, considere [configurar um node de fallback](./fallback) e [testar se ele funciona](./fallback#testando-os-clientes-de-fallback).
Com um fallback configurado, o Smart Node e o seu cliente de Consensus mudarão automaticamente para ele enquanto o seu cliente de Execution principal ressincroniza, e voltarão assim que ele estiver sincronizado.
:::

### Verifique qual banco de dados você tem

Execute:

```shell
rocketpool service get-db-details
```

| Saída                                                                           | O que significa                                                                            |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `Nethermind is using FlatDB. Manual state pruning is not needed or supported.`  | Você não precisa fazer pruning. O restante desta página não se aplica a você.              |
| `Nethermind is using the legacy Patricia database. State pruning is supported.` | Siga os passos de pruning abaixo quando o seu disco começar a encher.                      |
| `Nethermind has no persisted state database yet.`                               | O Nethermind ainda não gravou nenhum estado (por exemplo, logo após uma ressincronização). |

::: tip NOTA
`get-db-details` requer que o contêiner do seu cliente de Execution esteja em execução.
Ele informa apenas o formato do banco de dados. Em um node Archive, ele ainda pode indicar que o pruning do estado é suportado, mas nodes Archive não podem passar por pruning.
:::

### FlatInTrie em sistemas com 16 GiB de RAM ou menos

Quando o Nethermind sincroniza um novo banco de dados em uma máquina com **16 GiB de RAM ou menos**, o Smart Node seleciona o layout FlatDB **FlatInTrie** do Nethermind, que é mais adequado para sistemas com menos memória.
Essa escolha é salva junto com o banco de dados, portanto não mudará se você reiniciar ou adicionar mais RAM depois.
Ela só é redefinida quando você ressincroniza com `rocketpool service resync-eth1`.

### Configurações que se aplicam apenas ao banco de dados legado

As seguintes configurações do Nethermind em `rocketpool service config` afetam apenas bancos de dados Patricia legados e são ignoradas com o FlatDB:

- In-Memory Pruning Cache Size
- Full Prune Memory Budget Size
- Prune threshold (MB)
- Full pruning parallelism

::: tip NOTA
O FlatDB elimina a necessidade de fazer pruning do **estado**. Ele não altera quanto **histórico** (corpos de blocos e recibos) o seu node mantém.
Isso continua sendo controlado pela sua configuração **Pruning Mode**. Veja [Expiração do Histórico do Cliente de Execution](./maintenance/history-expiry).
:::

## Migrando o Geth para Pebble v2

Se você executa o **Geth** e o banco de dados ainda está no Pebble v1, migre-o no lugar com:

```shell
rocketpool service migrate-geth
```

Isso desliga o Geth, migra do Pebble v1 → v2 e depois o reinicia. **Não** é a mesma coisa que `prune-eth1`, e o nome do comando é **`migrate-geth`** (não `migrate-eth1`).

::: warning AVISO
O Geth fica offline durante toda a migração. Sem um [nó de fallback](./fallback), você vai perder atestações e propostas até que ela termine.
:::

Confirme o prompt, ou passe `--yes` para pulá-lo. Acompanhe o progresso com:

```shell
rocketpool service logs eth1
```

Não interrompa o contêiner até que a migração seja concluída.
