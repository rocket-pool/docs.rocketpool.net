# Pruning the Execution Client

::: tip NOTE
This page is the **offline / online prune** path for `geth` and `nethermind` (`rocketpool service prune-eth1`).

The usual way to keep disk use in check is **Rolling History Expiry** (the default Pruning Mode). Nethermind, Besu, Reth, and Erigon drop bodies and receipts older than about one year; Geth uses pre-Prague history expiry instead. See [Execution Client History Expiry](./maintenance/history-expiry).

:::

If you use `geth` or `nethermind` as your primary Execution client, you will likely notice that your node's free disk space slowly decreases over time.
The Execution client is by far the biggest contributor to this; depending on how much RAM you allocated to its cache during `rocketpool service config`, it can grow at a rate of several gigabytes per day!

To handle this, Execution clients provide a special function called **pruning** that lets them scan and clean up their database safely to reclaim some free space.
Every node operator using Geth or Nethermind will have to prune it eventually.

If you have a 2 TB SSD, you can usually go for months between rounds of pruning.
For 1 TB SSD users, you will have to prune more frequently.

If you have [the Grafana dashboard](./grafana) enabled, a good rule of thumb is to start thinking about pruning your Execution client when your node's used disk space exceeds 80%.

When you decide that it's time, the Smart Node comes with the ability to prune it for you upon request.
Read below to learn how it works, and what to expect.

::: warning NOTE
Pruning your Execution client is only possible in Docker Mode.

If you use your own Execution client, such as an external client in Hybrid mode or Native mode, you cannot use the Smart Node to prune the Execution client.
You will need to do it manually.
Please refer to the documentation for your Execution client to learn how to prune it.
:::

## Nethermind 2.0 and FlatDB

Starting with Smart Node v1.24.3, the Smart Node uses **Nethermind 2.0**. Nethermind 2.0 stores new databases in a format called **FlatDB**.
FlatDB does not need manual state pruning, and does not support it. If your Nethermind database uses FlatDB, you do not need `rocketpool service prune-eth1` at all.

Existing Nethermind databases are **not** converted. If your node was synced before Nethermind 2.0, it keeps using the legacy **Patricia** database and you can keep pruning it as described on this page.
The only way to move to FlatDB is to resync your Execution client with `rocketpool service resync-eth1`.

::: warning NOTE
Before you resync, consider [setting up a fallback node](./fallback) and [testing that it works](./fallback#testing-the-fallback-clients).
With a fallback configured, the Smart Node and your Consensus client will automatically switch to it while your primary Execution client resyncs, and switch back once it is synced.
:::

### Check which database you have

Run:

```shell
rocketpool service get-db-details
```

| Output                                                                          | What it means                                                                 |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `Nethermind is using FlatDB. Manual state pruning is not needed or supported.`  | You do not need to prune. The rest of this page does not apply to you.        |
| `Nethermind is using the legacy Patricia database. State pruning is supported.` | Follow the pruning steps below when your disk starts to fill up.              |
| `Nethermind has no persisted state database yet.`                               | Nethermind has not written any state yet (for example, right after a resync). |

::: tip NOTE
`get-db-details` requires your Execution client container to be running.
It only reports the database format. On an Archive node it may still say that state pruning is supported, but Archive nodes cannot be pruned.
:::

### FlatInTrie on systems with 16 GiB of RAM or less

When Nethermind syncs a new database on a machine with **16 GiB of RAM or less**, the Smart Node selects Nethermind's **FlatInTrie** FlatDB layout, which is better suited to systems with less memory.
This choice is saved alongside the database, so it will not change if you restart or later add more RAM.
It is only reset when you resync with `rocketpool service resync-eth1`.

### Settings that only apply to the legacy database

The following Nethermind settings in `rocketpool service config` only affect legacy Patricia databases, and are ignored with FlatDB:

- In-Memory Pruning Cache Size
- Full Prune Memory Budget Size
- Prune threshold (MB)
- Full pruning parallelism

::: tip NOTE
FlatDB removes the need to prune **state**. It does not change how much **history** (block bodies and receipts) your node keeps.
That is still controlled by your **Pruning Mode** setting. See [Execution Client History Expiry](./maintenance/history-expiry).
:::

## Starting a Prune

Select the client you're using from the tabs below.

      ```shell
      rocketpool service prune-eth1
      ```

      If you do not have a fallback client pair enabled, you will receive the following warning:

      ```
      This will shut down your main execution client and prune its database, freeing up disk space.

      ```

      If you do have one enabled, you will see the following prompt instead:

      ```
      This will shut down your main execution client and prune its database, freeing up disk space.
      Once pruning is complete, your execution client will restart automatically.

      You have fallback clients enabled. Rocket Pool (and your consensus client) will use that while the main client is pruning.
      Are you sure you want to prune your main execution client? [y/n]
      ```

      If you accept, you'll see a few details as the Smart Node prepares things; it should end with a success message:

      ```
      Are you sure you want to prune your main ETH1 client? [y/n]
      y

      Your disk has 303 GiB free, which is enough to prune.
      Stopping rocketpool_eth1...
      Provisioning pruning on volume rocketpool_eth1clientdata...
      Restarting rocketpool_eth1...

      Done! Your main ETH1 client is now pruning. You can follow its progress with `rocketpool service logs eth1`.
      Once it's done, it will restart automatically and resume normal operation.
      NOTE: While pruning, you **cannot** interrupt the client (e.g. by restarting) or you risk corrupting the database!
      You must let it run to completion!
      ```

      With that, Geth is now pruning and you're all set!
      You can follow its progress with:

      ```shell
      rocketpool service logs eth1
      ```

      Once it's done pruning, it will restart automatically and the Smart Node will resume using it again instead of your fallback.
    </Tab>

## Migrating Geth to Pebble v2

If you run **Geth** and the database is still on Pebble v1, migrate it in place with:

```shell
rocketpool service migrate-geth
```

This shuts Geth down, migrates Pebble v1 → v2, then restarts it. It is **not** the same as `prune-eth1`, and the command name is **`migrate-geth`** (not `migrate-eth1`).

::: warning NOTE
Geth is offline for the duration of the migration. Without a [fallback node](./fallback), you will miss attestations and proposals until it is finished.
:::

Confirm the prompt, or pass `--yes` to skip it. Follow progress with:

```shell
rocketpool service logs eth1
```

Do not interrupt the container until the migration completes.
