# Pruning des Execution Clients

::: tip HINWEIS
Diese Seite beschreibt den Weg des **Offline-/Online-Prunings** für `geth` und `nethermind` (`rocketpool service prune-eth1`).

Der übliche Weg, den Speicherverbrauch im Griff zu behalten, ist **Rolling History Expiry** (der Standard-Pruning-Modus). Nethermind, Besu, Reth und Erigon verwerfen Blockkörper und Belege, die älter als etwa ein Jahr sind; Geth verwendet stattdessen den Ablauf der Historie vor Prague. Siehe [Ablauf der Historie des Execution-Clients](./maintenance/history-expiry).

:::

Wenn Sie `geth` oder `nethermind` als Ihren primären Execution Client verwenden, werden Sie wahrscheinlich bemerken, dass der freie Speicherplatz Ihres Nodes im Laufe der Zeit langsam abnimmt.
Der Execution Client ist bei weitem der größte Beitragszahler hierzu; abhängig davon, wie viel RAM Sie während `rocketpool service config` seinem Cache zugewiesen haben, kann er mit einer Rate von mehreren Gigabyte pro Tag wachsen!

Um damit umzugehen, bieten Execution Clients eine spezielle Funktion namens **Pruning**, die es ihnen ermöglicht, ihre Datenbank sicher zu scannen und aufzuräumen, um freien Speicherplatz zurückzugewinnen.
Jeder Node Operator, der Geth oder Nethermind verwendet, wird es irgendwann prunen müssen.

Wenn Sie eine 2 TB SSD haben, können Sie normalerweise Monate zwischen den Pruning-Runden vergehen lassen.
Für 1 TB SSD-Benutzer müssen Sie häufiger prunen.

Wenn Sie das [Grafana Dashboard](./grafana) aktiviert haben, ist eine gute Faustregel, über das Pruning Ihres Execution Clients nachzudenken, wenn Ihr verwendeter Speicherplatz des Nodes 80% überschreitet.

Wenn Sie entscheiden, dass es Zeit ist, verfügt der Smart Node über die Möglichkeit, es auf Anfrage für Sie zu prunen.
Lesen Sie unten, um zu erfahren, wie es funktioniert und was Sie erwarten können.

::: warning HINWEIS
Das Pruning Ihres Execution Clients ist nur im Docker Mode möglich.

Wenn Sie Ihren eigenen Execution Client verwenden, wie z.B. einen externen Client im Hybrid-Modus oder Native-Modus, können Sie den Smart Node nicht zum Pruning des Execution Clients verwenden.
Sie müssen es manuell durchführen.
Bitte konsultieren Sie die Dokumentation für Ihren Execution Client, um zu erfahren, wie Sie ihn prunen.
:::

## Nethermind 2.0 und FlatDB

Ab Smart Node v1.24.3 verwendet der Smart Node **Nethermind 2.0**. Nethermind 2.0 speichert neue Datenbanken in einem Format namens **FlatDB**.
FlatDB benötigt kein manuelles State-Pruning und unterstützt es auch nicht. Wenn Ihre Nethermind-Datenbank FlatDB verwendet, benötigen Sie `rocketpool service prune-eth1` überhaupt nicht.

Bestehende Nethermind-Datenbanken werden **nicht** konvertiert. Wenn Ihr Node vor Nethermind 2.0 synchronisiert wurde, verwendet er weiterhin die alte **Patricia**-Datenbank, und Sie können sie weiterhin wie auf dieser Seite beschrieben prunen.
Die einzige Möglichkeit, auf FlatDB umzusteigen, ist eine Neusynchronisierung Ihres Execution Clients mit `rocketpool service resync-eth1`.

::: warning HINWEIS
Ziehen Sie vor der Neusynchronisierung in Betracht, [einen Fallback Node einzurichten](./fallback) und [zu testen, ob er funktioniert](./fallback#testen-der-fallback-clients).
Mit einem konfigurierten Fallback wechseln der Smart Node und Ihr Consensus Client automatisch zu diesem, während Ihr primärer Execution Client neu synchronisiert, und wechseln zurück, sobald er synchronisiert ist.
:::

### Prüfen, welche Datenbank Sie haben

Führen Sie aus:

```shell
rocketpool service get-db-details
```

| Ausgabe                                                                         | Bedeutung                                                                                          |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `Nethermind is using FlatDB. Manual state pruning is not needed or supported.`  | Sie müssen nicht prunen. Der Rest dieser Seite betrifft Sie nicht.                                 |
| `Nethermind is using the legacy Patricia database. State pruning is supported.` | Folgen Sie den Pruning-Schritten unten, wenn sich Ihre Festplatte zu füllen beginnt.               |
| `Nethermind has no persisted state database yet.`                               | Nethermind hat noch keinen State geschrieben (zum Beispiel direkt nach einer Neusynchronisierung). |

::: tip HINWEIS
`get-db-details` setzt voraus, dass Ihr Execution-Client-Container läuft.
Es meldet nur das Datenbankformat. Auf einem Archive Node kann es dennoch melden, dass State-Pruning unterstützt wird, aber Archive Nodes können nicht gepruned werden.
:::

### FlatInTrie auf Systemen mit 16 GiB RAM oder weniger

Wenn Nethermind eine neue Datenbank auf einem Rechner mit **16 GiB RAM oder weniger** synchronisiert, wählt der Smart Node das **FlatInTrie**-FlatDB-Layout von Nethermind, das für Systeme mit weniger Arbeitsspeicher besser geeignet ist.
Diese Wahl wird zusammen mit der Datenbank gespeichert, sodass sie sich nicht ändert, wenn Sie neu starten oder später mehr RAM hinzufügen.
Sie wird nur zurückgesetzt, wenn Sie mit `rocketpool service resync-eth1` neu synchronisieren.

### Einstellungen, die nur für die alte Datenbank gelten

Die folgenden Nethermind-Einstellungen in `rocketpool service config` wirken sich nur auf alte Patricia-Datenbanken aus und werden bei FlatDB ignoriert:

- In-Memory Pruning Cache Size
- Full Prune Memory Budget Size
- Prune threshold (MB)
- Full pruning parallelism

::: tip HINWEIS
FlatDB macht das Pruning des **States** überflüssig. Es ändert nicht, wie viel **Historie** (Blockkörper und Belege) Ihr Node speichert.
Dies wird weiterhin über Ihre Einstellung **Pruning Mode** gesteuert. Siehe [Ablauf der Historie des Execution-Clients](./maintenance/history-expiry).
:::

## Geth auf Pebble v2 migrieren

Wenn Sie **Geth** betreiben und die Datenbank noch auf Pebble v1 läuft, migrieren Sie sie an Ort und Stelle mit:

```shell
rocketpool service migrate-geth
```

Dabei wird Geth heruntergefahren, die Datenbank von Pebble v1 → v2 migriert und anschließend neu gestartet. Das ist **nicht** dasselbe wie `prune-eth1`, und der Befehl heißt **`migrate-geth`** (nicht `migrate-eth1`).

::: warning WARNUNG
Geth ist während der gesamten Migration offline. Ohne einen [Fallback-Node](./fallback) verpassen Sie Attestierungen und Blockvorschläge, bis sie abgeschlossen ist.
:::

Bestätigen Sie die Abfrage oder übergeben Sie `--yes`, um sie zu überspringen. Verfolgen Sie den Fortschritt mit:

```shell
rocketpool service logs eth1
```

Unterbrechen Sie den Container nicht, bevor die Migration abgeschlossen ist.
