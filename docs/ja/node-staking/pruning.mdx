# Execution Clientのプルーニング

::: tip 注記
このページは、`geth`と`nethermind`向けの**オフライン／オンラインプルーニング**の手順です(`rocketpool service prune-eth1`)。

ディスク使用量を抑える通常の方法は**Rolling History Expiry**(デフォルトのPruning Mode)です。Nethermind、Besu、Reth、Erigonは約1年より古いボディとレシートを破棄します。Gethは代わりにPrague以前の履歴削除を使用します。[Execution clientの履歴削除](./maintenance/history-expiry)を参照してください。

:::

主要なExecution clientとして`geth`または`nethermind`を使用している場合、ノードの空きディスク容量が時間の経過とともにゆっくりと減少していくことに気付くでしょう。
Execution clientはこれに最も大きく寄与します。`rocketpool service config`でキャッシュに割り当てたRAMの量に応じて、1日あたり数ギガバイトの速度で増加することがあります。

これに対処するため、Execution clientは**プルーニング**と呼ばれる特別な機能を提供しており、安全にデータベースをスキャンしてクリーンアップし、空き容量を回復できます。
GethまたはNethermindを使用するすべてのNode Operatorは、いずれプルーニングを行う必要があります。

2 TBのSSDを使用している場合、通常、プルーニングの間隔は数ヶ月になります。
1 TBのSSDユーザーの場合、より頻繁にプルーニングする必要があります。

[Grafanaダッシュボード](./grafana)を有効にしている場合、ノードの使用済みディスク容量が80%を超えたら、Execution clientのプルーニングを検討し始める良い目安になります。

プルーニングの時期が来たと判断したら、Smart Nodeはリクエストに応じてプルーニングを実行する機能を備えています。
以下を読んで、仕組みと予想される動作を学んでください。

::: warning 注記
Execution clientのプルーニングはDockerモードでのみ可能です。

Hybridモードの外部クライアントやNativeモードなど、独自のExecution clientを使用している場合、Smart Nodeを使用してExecution clientをプルーニングすることはできません。
手動で行う必要があります。
Execution clientのドキュメントを参照して、プルーニング方法を学んでください。
:::

## Nethermind 2.0とFlatDB

Smart Node v1.24.3以降、Smart Nodeは**Nethermind 2.0**を使用します。Nethermind 2.0は、新しいデータベースを**FlatDB**と呼ばれる形式で保存します。
FlatDBは手動のステートプルーニングを必要とせず、サポートもしていません。NethermindのデータベースがFlatDBを使用している場合、`rocketpool service prune-eth1`はまったく必要ありません。

既存のNethermindデータベースは変換**されません**。Nethermind 2.0より前に同期されたノードは、引き続きレガシーの**Patricia**データベースを使用するため、このページの説明どおりにプルーニングを続けられます。
FlatDBに移行する唯一の方法は、`rocketpool service resync-eth1`でExecution clientを再同期することです。

::: warning 注記
再同期する前に、[フォールバックノードを設定](./fallback)し、[正しく動作することをテスト](./fallback#フォールバッククライアントのテスト)することを検討してください。
フォールバックが設定されていれば、プライマリのExecution clientが再同期している間、Smart NodeとConsensus clientは自動的にフォールバックに切り替わり、同期が完了すると元に戻ります。
:::

### 使用しているデータベースの確認

次を実行します。

```shell
rocketpool service get-db-details
```

| 出力                                                                            | 意味                                                               |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `Nethermind is using FlatDB. Manual state pruning is not needed or supported.`  | プルーニングは不要です。このページの残りの内容は該当しません。     |
| `Nethermind is using the legacy Patricia database. State pruning is supported.` | ディスクが埋まり始めたら、以下のプルーニング手順に従ってください。 |
| `Nethermind has no persisted state database yet.`                               | Nethermindはまだステートを書き込んでいません(例:再同期の直後)。    |

::: tip 注記
`get-db-details`を使用するには、Execution clientのコンテナが実行中である必要があります。
このコマンドはデータベース形式のみを報告します。Archiveノードではステートプルーニングがサポートされていると表示される場合がありますが、Archiveノードはプルーニングできません。
:::

### RAMが16 GiB以下のシステムでのFlatInTrie

**RAMが16 GiB以下**のマシンでNethermindが新しいデータベースを同期する場合、Smart Nodeはメモリの少ないシステムにより適したNethermindの**FlatInTrie** FlatDBレイアウトを選択します。
この選択はデータベースと一緒に保存されるため、再起動したり後からRAMを増設したりしても変わりません。
リセットされるのは、`rocketpool service resync-eth1`で再同期した場合のみです。

### レガシーデータベースにのみ適用される設定

`rocketpool service config`の以下のNethermind設定はレガシーのPatriciaデータベースにのみ影響し、FlatDBでは無視されます。

- In-Memory Pruning Cache Size
- Full Prune Memory Budget Size
- Prune threshold (MB)
- Full pruning parallelism

::: tip 注記
FlatDBにより**ステート**のプルーニングは不要になります。ただし、ノードが保持する**履歴**(ブロック本体とレシート)の量は変わりません。
これは引き続き**Pruning Mode**設定で制御されます。[Execution clientの履歴削除](./maintenance/history-expiry)を参照してください。
:::

## GethのPebble v2への移行

**Geth**を実行していてデータベースがまだPebble v1の場合は、次のコマンドでその場で移行できます:

```shell
rocketpool service migrate-geth
```

このコマンドはGethをシャットダウンし、Pebble v1 → v2への移行を行った後、再起動します。これは`prune-eth1`とは**異なり**、コマンド名は**`migrate-geth`**です(`migrate-eth1`ではありません)。

::: warning 警告
移行中、Gethはオフラインになります。[フォールバックノード](./fallback)がない場合、移行が完了するまでアテステーションとブロック提案を逃します。
:::

プロンプトで確認するか、`--yes`を渡してスキップしてください。進行状況は次のコマンドで確認できます:

```shell
rocketpool service logs eth1
```

移行が完了するまでコンテナを中断しないでください。
