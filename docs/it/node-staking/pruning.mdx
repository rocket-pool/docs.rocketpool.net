# Pruning dell'Execution Client

::: tip NOTA
Questa pagina descrive il percorso di **potatura offline / online** per `geth` e `nethermind` (`rocketpool service prune-eth1`).

Il modo consueto per tenere sotto controllo l'uso del disco è **Rolling History Expiry** (il Pruning Mode predefinito). Nethermind, Besu, Reth ed Erigon eliminano corpi e ricevute più vecchi di circa un anno; Geth utilizza invece la scadenza della cronologia precedente a Prague. Vedi [Scadenza della Cronologia del Client Execution](./maintenance/history-expiry).

:::

Se utilizzi `geth` o `nethermind` come client Execution primario, probabilmente noterai che lo spazio libero su disco del tuo nodo diminuisce lentamente nel tempo.
Il client Execution è di gran lunga il maggiore contributore a questo; a seconda di quanta RAM hai allocato alla sua cache durante `rocketpool service config`, può crescere a un ritmo di diversi gigabyte al giorno!

Per gestire questo, i client Execution forniscono una funzione speciale chiamata **pruning** che consente loro di scansionare e pulire in sicurezza il loro database per recuperare spazio libero.
Ogni node operator che utilizza Geth o Nethermind dovrà eventualmente eseguire il pruning.

Se hai un SSD da 2 TB, di solito puoi andare avanti per mesi tra i cicli di pruning.
Per gli utenti di SSD da 1 TB, dovrai eseguire il pruning più frequentemente.

Se hai abilitato la [dashboard Grafana](./grafana), una buona regola generale è iniziare a pensare al pruning del tuo client Execution quando lo spazio su disco utilizzato del tuo nodo supera l'80%.

Quando decidi che è il momento, lo Smart Node viene fornito con la possibilità di eseguire il pruning per te su richiesta.
Leggi di seguito per sapere come funziona e cosa aspettarti.

::: warning NOTA
Il pruning del tuo client Execution è possibile solo in Docker Mode.

Se utilizzi il tuo client Execution, come un client esterno in modalità Hybrid o Native mode, non puoi utilizzare lo Smart Node per eseguire il pruning del client Execution.
Dovrai farlo manualmente.
Si prega di fare riferimento alla documentazione del tuo client Execution per imparare come eseguirne il pruning.
:::

## Nethermind 2.0 e FlatDB

A partire da Smart Node v1.24.3, lo Smart Node usa **Nethermind 2.0**. Nethermind 2.0 archivia i nuovi database in un formato chiamato **FlatDB**.
FlatDB non necessita del pruning manuale dello stato e non lo supporta. Se il tuo database Nethermind usa FlatDB, non hai affatto bisogno di `rocketpool service prune-eth1`.

I database Nethermind esistenti **non** vengono convertiti. Se il tuo nodo è stato sincronizzato prima di Nethermind 2.0, continua a usare il database **Patricia** legacy e puoi continuare a eseguirne il pruning come descritto in questa pagina.
L'unico modo per passare a FlatDB è risincronizzare il tuo client di Execution con `rocketpool service resync-eth1`.

::: warning NOTA
Prima di risincronizzare, valuta di [configurare un nodo di fallback](./fallback) e di [verificare che funzioni](./fallback#testare-i-client-di-fallback).
Con un fallback configurato, lo Smart Node e il tuo client di Consensus passeranno automaticamente a esso mentre il client di Execution principale si risincronizza, e torneranno indietro una volta completata la sincronizzazione.
:::

### Verifica quale database hai

Esegui:

```shell
rocketpool service get-db-details
```

| Output                                                                          | Cosa significa                                                                                  |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `Nethermind is using FlatDB. Manual state pruning is not needed or supported.`  | Non è necessario eseguire il pruning. Il resto di questa pagina non ti riguarda.                |
| `Nethermind is using the legacy Patricia database. State pruning is supported.` | Segui i passaggi di pruning qui sotto quando il disco inizia a riempirsi.                       |
| `Nethermind has no persisted state database yet.`                               | Nethermind non ha ancora scritto alcuno stato (ad esempio, subito dopo una risincronizzazione). |

::: tip NOTA
`get-db-details` richiede che il container del tuo client di Execution sia in esecuzione.
Riporta solo il formato del database. Su un nodo Archive potrebbe comunque indicare che il pruning dello stato è supportato, ma i nodi Archive non possono essere sottoposti a pruning.
:::

### FlatInTrie su sistemi con 16 GiB di RAM o meno

Quando Nethermind sincronizza un nuovo database su una macchina con **16 GiB di RAM o meno**, lo Smart Node seleziona il layout FlatDB **FlatInTrie** di Nethermind, più adatto ai sistemi con meno memoria.
Questa scelta viene salvata insieme al database, quindi non cambierà se riavvii o aggiungi altra RAM in seguito.
Viene reimpostata solo quando risincronizzi con `rocketpool service resync-eth1`.

### Impostazioni che si applicano solo al database legacy

Le seguenti impostazioni di Nethermind in `rocketpool service config` riguardano solo i database Patricia legacy e vengono ignorate con FlatDB:

- In-Memory Pruning Cache Size
- Full Prune Memory Budget Size
- Prune threshold (MB)
- Full pruning parallelism

::: tip NOTA
FlatDB elimina la necessità di eseguire il pruning dello **stato**. Non cambia la quantità di **cronologia** (corpi dei blocchi e ricevute) che il tuo nodo conserva.
Questa è ancora controllata dall'impostazione **Pruning Mode**. Vedi [Scadenza della cronologia del client di Execution](./maintenance/history-expiry).
:::

## Migrare Geth a Pebble v2

Se esegui **Geth** e il database è ancora su Pebble v1, migralo sul posto con:

```shell
rocketpool service migrate-geth
```

Questo comando arresta Geth, migra il database da Pebble v1 → v2 e poi lo riavvia. **Non** è la stessa cosa di `prune-eth1`, e il nome del comando è **`migrate-geth`** (non `migrate-eth1`).

::: warning ATTENZIONE
Geth resta offline per tutta la durata della migrazione. Senza un [nodo di fallback](./fallback), perderai attestazioni e proposte fino al termine.
:::

Conferma il prompt, oppure passa `--yes` per saltarlo. Segui i progressi con:

```shell
rocketpool service logs eth1
```

Non interrompere il container finché la migrazione non è completata.
