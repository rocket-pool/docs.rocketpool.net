# Podar el Cliente de Ejecución

::: tip NOTA
Esta página describe la ruta de **poda offline / online** para `geth` y `nethermind` (`rocketpool service prune-eth1`).

La forma habitual de mantener el uso de disco bajo control es **Rolling History Expiry** (el Pruning Mode predeterminado). Nethermind, Besu, Reth y Erigon descartan cuerpos y recibos de más de un año de antigüedad aproximadamente; Geth utiliza en su lugar la caducidad del historial anterior a Prague. Consulta [Caducidad del Historial del Cliente de Ejecución](./maintenance/history-expiry).

:::

Si usas `geth` o `nethermind` como tu cliente de Ejecución principal, probablemente notarás que el espacio libre en disco de tu nodo disminuye lentamente con el tiempo.
El cliente de Ejecución es, con mucho, el mayor contribuyente a esto; ¡dependiendo de cuánta RAM asignaste a su caché durante `rocketpool service config`, puede crecer a una tasa de varios gigabytes por día!

Para manejar esto, los clientes de Ejecución proporcionan una función especial llamada **podado** que les permite escanear y limpiar su base de datos de forma segura para recuperar algo de espacio libre.
Todo operador de nodo que use Geth o Nethermind tendrá que podarlo eventualmente.

Si tienes un SSD de 2 TB, generalmente puedes pasar meses entre rondas de podado.
Para usuarios de SSD de 1 TB, tendrás que podar con más frecuencia.

Si tienes [el panel de Grafana](./grafana) habilitado, una buena regla general es comenzar a pensar en podar tu cliente de Ejecución cuando el espacio en disco usado de tu nodo supere el 80%.

Cuando decidas que es hora, el Smart Node viene con la capacidad de podarlo por ti bajo petición.
Lee a continuación para aprender cómo funciona y qué esperar.

::: warning NOTA
Podar tu cliente de Ejecución solo es posible en Docker Mode.

Si usas tu propio cliente de Ejecución, como un cliente externo en modo Hybrid o modo Native, no puedes usar el Smart Node para podar el cliente de Ejecución.
Tendrás que hacerlo manualmente.
Consulta la documentación de tu cliente de Ejecución para aprender cómo podarlo.
:::

## Nethermind 2.0 y FlatDB

A partir de Smart Node v1.24.3, el Smart Node usa **Nethermind 2.0**. Nethermind 2.0 almacena las bases de datos nuevas en un formato llamado **FlatDB**.
FlatDB no necesita podado manual del estado, y tampoco lo admite. Si tu base de datos de Nethermind usa FlatDB, no necesitas `rocketpool service prune-eth1` en absoluto.

Las bases de datos de Nethermind existentes **no** se convierten. Si tu nodo se sincronizó antes de Nethermind 2.0, sigue usando la base de datos **Patricia** heredada y puedes seguir podándola como se describe en esta página.
La única forma de pasar a FlatDB es resincronizar tu cliente de Execution con `rocketpool service resync-eth1`.

::: warning NOTA
Antes de resincronizar, considera [configurar un nodo de respaldo](./fallback) y [comprobar que funciona](./fallback#probar-los-clientes-de-respaldo).
Con un respaldo configurado, el Smart Node y tu cliente de Consensus cambiarán automáticamente a él mientras tu cliente de Execution principal se resincroniza, y volverán al principal una vez sincronizado.
:::

### Comprueba qué base de datos tienes

Ejecuta:

```shell
rocketpool service get-db-details
```

| Salida                                                                          | Qué significa                                                                                    |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `Nethermind is using FlatDB. Manual state pruning is not needed or supported.`  | No necesitas podar. El resto de esta página no te aplica.                                        |
| `Nethermind is using the legacy Patricia database. State pruning is supported.` | Sigue los pasos de podado de abajo cuando tu disco empiece a llenarse.                           |
| `Nethermind has no persisted state database yet.`                               | Nethermind aún no ha escrito ningún estado (por ejemplo, justo después de una resincronización). |

::: tip NOTA
`get-db-details` requiere que el contenedor de tu cliente de Execution esté en ejecución.
Solo informa del formato de la base de datos. En un nodo Archive puede seguir indicando que el podado del estado es compatible, pero los nodos Archive no se pueden podar.
:::

### FlatInTrie en sistemas con 16 GiB de RAM o menos

Cuando Nethermind sincroniza una base de datos nueva en una máquina con **16 GiB de RAM o menos**, el Smart Node selecciona el diseño FlatDB **FlatInTrie** de Nethermind, que se adapta mejor a sistemas con menos memoria.
Esta elección se guarda junto con la base de datos, por lo que no cambiará si reinicias o añades más RAM más adelante.
Solo se restablece cuando resincronizas con `rocketpool service resync-eth1`.

### Ajustes que solo se aplican a la base de datos heredada

Los siguientes ajustes de Nethermind en `rocketpool service config` solo afectan a las bases de datos Patricia heredadas y se ignoran con FlatDB:

- In-Memory Pruning Cache Size
- Full Prune Memory Budget Size
- Prune threshold (MB)
- Full pruning parallelism

::: tip NOTA
FlatDB elimina la necesidad de podar el **estado**. No cambia cuánto **historial** (cuerpos de bloque y recibos) conserva tu nodo.
Eso sigue controlado por tu ajuste **Pruning Mode**. Consulta [Expiración del historial del cliente de Execution](./maintenance/history-expiry).
:::

## Migrar Geth a Pebble v2

Si ejecutas **Geth** y la base de datos todavía está en Pebble v1, mígrala in situ con:

```shell
rocketpool service migrate-geth
```

Esto apaga Geth, migra de Pebble v1 → v2 y luego lo reinicia. **No** es lo mismo que `prune-eth1`, y el nombre del comando es **`migrate-geth`** (no `migrate-eth1`).

::: warning ADVERTENCIA
Geth permanece sin conexión durante toda la migración. Sin un [nodo de respaldo](./fallback), perderás atestaciones y propuestas hasta que termine.
:::

Confirma el mensaje, o pasa `--yes` para omitirlo. Sigue el progreso con:

```shell
rocketpool service logs eth1
```

No interrumpas el contenedor hasta que la migración se complete.
